🔄 5. Transactions & Consistency

SERIALIZABLE — Always, By Default

CockroachDB's default isolation level is SERIALIZABLE. There is no READ COMMITTED default and no setting to silently weaken it.

What this means in practice:

  • Concurrent transactions behave as if they ran one at a time
  • No dirty reads, no non-repeatable reads, no phantom reads, no write skew
  • You pay for it with transaction retries under contention
  • Application code must handle retries gracefully

As of v23.2, READ COMMITTED is available opt-in — but the course defaults assume SERIALIZABLE.

MVCC — Many Versions, No Locks for Readers

Every key in CockroachDB is stored with a timestamp. A read at time T returns the most recent version at or before T.

MVCC key layout (simplified)


/users/'abc'/email   @ T=1000  → "old@example.com"     (committed)
/users/'abc'/email   @ T=2000  → "new@example.com"     (committed)
/users/'abc'/email   @ T=2500  → "newer@example.com"   (write intent — uncommitted)
  • Readers don't block writers — a read at T=1500 sees the T=1000 version
  • Writers don't block readers — same reason
  • Write-write conflicts resolve via Raft and transaction ordering

Write Intents & Conflict Detection

When a transaction writes a key, it leaves a write intent — a provisional value tagged with the transaction's ID and timestamp.

Two transactions touching the same row


Txn A:  BEGIN; UPDATE balance SET amt = amt - 100 WHERE id = 'x';   -- intent written
Txn B:  BEGIN; UPDATE balance SET amt = amt + 50  WHERE id = 'x';

    → Txn B sees A's intent. Txn B WAITS (or pushes A's timestamp).
    → When A commits, its intent becomes a committed MVCC version.
    → Txn B then re-reads and proceeds — possibly at a later timestamp.

If serializability would be violated, the conflict is resolved by retrying one of the transactions with a fresh read timestamp. The client sees a retryable error.

Retryable Errors — Your App Must Handle Them

SQLSTATE 40001 — serialization_failure


ERROR: restart transaction: TransactionRetryWithProtoRefreshError:
       WriteTooOldError: write at timestamp ... too old; wrote at ...
       SQLSTATE: 40001

The retry rule: the client must run the entire transaction again, from BEGIN to COMMIT. Not just the last statement.

  • Most drivers ship a retry helper (e.g. crdb.run_transaction() in psycopg)
  • Most ORMs need a wrapper — see the integrations section
  • The cluster will also do internal retries for many short, single-statement transactions before surfacing an error

Retry Loop — Pseudocode

Application-side retry pattern


import psycopg2
from psycopg2 import errors

MAX_RETRIES = 5

def transfer(conn, src, dst, amount):
    for attempt in range(MAX_RETRIES):
        try:
            with conn:                              # BEGIN
                with conn.cursor() as cur:
                    cur.execute(
                        "UPDATE accounts SET balance = balance - %s WHERE id = %s",
                        (amount, src))
                    cur.execute(
                        "UPDATE accounts SET balance = balance + %s WHERE id = %s",
                        (amount, dst))
            return                                  # COMMIT successful
        except errors.SerializationFailure:
            # 40001 — retry the entire transaction
            continue
    raise RuntimeError("transfer failed after retries")

Common mistake: catching and ignoring the error. The transaction is already aborted — the next statement on that connection will fail until you start fresh.

Follower Reads & AS OF SYSTEM TIME

For read-only queries that can tolerate slightly stale data, you can read from any replica, not just the leaseholder:

Two flavors


-- Exact-time historical read (default ~4.8s in the past)
SELECT * FROM orders AS OF SYSTEM TIME follower_read_timestamp();

-- Read at a specific HLC timestamp
SELECT * FROM orders AS OF SYSTEM TIME '2026-05-22 10:00:00';

-- Whole transaction at a single past timestamp (useful for reporting)
BEGIN;
SET TRANSACTION AS OF SYSTEM TIME follower_read_timestamp();
SELECT ... FROM big_table JOIN ...;
COMMIT;
  • Cuts cross-region latency dramatically — read from the local replica
  • Skips contention with concurrent writes — historical reads can't conflict
  • Tradeoff: data is stale (typically by 4-5 seconds)

Contention Anti-Patterns

Anti-PatternSymptomFix
Single-row counter (UPDATE counters SET n = n + 1) All writes contend Sharded counter or message queue
Long-running read tx blocking writes Write intents pile up Use AS OF SYSTEM TIME for reports
SELECT * + UPDATE on same connection (no BEGIN) No atomicity, repeated retries Wrap in explicit BEGIN ... COMMIT
Bulk insert through one connection Sequential commits, slow Parallelize across connections, use multi-row INSERT

🔍 6. Query Optimization

Three Levels of EXPLAIN

CommandWhat it showsRuns the query?
EXPLAIN Plan tree + estimated row counts No
EXPLAIN ANALYZE Plan + actual times, rows, network I/O Yes
EXPLAIN ANALYZE (DEBUG) Produces a downloadable bundle for support Yes

Always start with EXPLAIN ANALYZE — estimated rows are useful, but actual rows tell you where the optimizer was wrong.

Reading an EXPLAIN ANALYZE

Annotated output


EXPLAIN ANALYZE SELECT name, total FROM orders
WHERE customer_id = '550e8400-...' AND status = 'open';

planning time: 0.4ms
execution time: 2.1ms                        ← total wall-clock
distribution: local
vectorized: true

• filter
  estimated row count: 3
  actual row count: 2                        ← matches estimate (good!)
  filter: status = 'open'
  │
  └── • scan
        nodes: n2                            ← where it ran
        regions: us-east1
        actual row count: 12
        KV time: 1.4ms                       ← bulk of the cost
        table: orders@orders_customer_id_idx
        spans: [/'550e8400-...' - /'550e8400-...']   ← single-key span

Statistics & the Cost Model

  • CockroachDB collects table statistics automatically (sampled, periodic)
  • Stats include row count, distinct values per column, null %, histograms
  • The optimizer uses stats to estimate selectivity and pick the cheapest plan
  • After bulk loads or large schema changes, refresh stats manually:

Refreshing & inspecting stats


-- Force a refresh on one table
CREATE STATISTICS my_stats FROM orders;

-- See what's there
SHOW STATISTICS FOR TABLE orders;

-- Per-column histogram
SHOW HISTOGRAM <histogram_id>;

Index Hints & Index Recommendations

Usually the optimizer picks well. When it doesn't, you have two levers:

Hint a specific index


SELECT * FROM orders@orders_customer_id_idx
WHERE customer_id = 'abc';

-- Force a full table scan (rarely useful, but available)
SELECT * FROM orders@{NO_INDEX_JOIN}
WHERE customer_id = 'abc';

CockroachDB will tell you when you're missing an index. Check the SQL Activity → Insights tab in the DB Console — it surfaces queries that would benefit from a new index, and even gives you the CREATE INDEX statement.

Common Slow-Query Patterns

Symptom in EXPLAIN ANALYZELikely causeFix
Full table scan, span [ - ] Missing index for predicate Add covering index
Index join shows ≫ rows than final result Index is too narrow Add STORING clause
Estimated rows ≪ actual rows Stale statistics CREATE STATISTICS manually
distribution: full for a small query Cross-range scan Narrow predicate or co-locate via composite PK
High KV time vs execution time Reading lots of keys to filter little Better index, partial index, or STORING

🌍 7. Multi-Region Topologies & Resilience

Multi-Region — Three Building Blocks

  1. Localities — every node is tagged with region, zone, etc.
  2. Survival goal — what level of failure should the database survive without going read/write unavailable?
  3. Table locality — where do the rows of a table live, and where are their leaseholders?

Get these three right and CockroachDB does the heavy lifting (replica placement, leaseholder placement, follower reads) automatically.

Localities — Tagging Nodes

Set at node startup


cockroach start \
  --locality=region=us-east1,zone=us-east1-b,rack=r4 \
  --join=...
  • Localities are hierarchical — left-to-right, broadest to narrowest
  • The cluster uses them to spread replicas across failure domains
  • Most multi-region clusters use at least region and zone
  • Misconfigured localities = your "multi-region" cluster may have every replica in one region

Defining the Cluster's Regions

SQL setup


-- Tell the database which regions it's deployed in
ALTER DATABASE bank SET PRIMARY REGION "us-east1";
ALTER DATABASE bank ADD REGION "us-west1";
ALTER DATABASE bank ADD REGION "europe-west1";

-- Inspect
SHOW REGIONS FROM DATABASE bank;

The primary region is the default home for new tables. ADD REGION adds more — each region must already have nodes running with the matching locality tag.

Survival Goals — What Should the DB Survive?

GoalToleratesReplicas needed per range
ZONE FAILURE (default) Loss of any 1 zone in the primary region 3 (across 3 zones in 1 region)
REGION FAILURE Loss of any 1 entire region 5 (across at least 3 regions)

Setting the goal


ALTER DATABASE bank SURVIVE REGION FAILURE;

Tradeoff: REGION FAILURE needs cross-region quorum on every write → write latency includes cross-region RTT. Always-on, but slower writes.

Table Locality — Where Do Rows Live?

LocalityBest forRead latencyWrite latency
REGIONAL BY TABLE Single-region apps, reference data per region Local in primary region Local in primary region
REGIONAL BY ROW User data with home regions (multi-tenant SaaS) Local for that row's region Local for that row's region
GLOBAL Rarely-changing, read-anywhere reference data Local everywhere Cross-region (slow)

REGIONAL BY ROW in Practice

Per-row geo-partitioning


ALTER DATABASE bank PRIMARY REGION "us-east1";
ALTER DATABASE bank ADD REGION "us-west1", "europe-west1";

CREATE TABLE customers (
  id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email     STRING UNIQUE,
  region    crdb_internal_region NOT VISIBLE AS (
              CASE
                WHEN email LIKE '%@%.eu' THEN 'europe-west1'
                ELSE 'us-east1'
              END
            ) STORED
) LOCALITY REGIONAL BY ROW AS region;

Each row's data and leaseholder live in the region named by its region column. A US-based customer's reads are local; an EU customer's reads are local. GDPR data-residency requirements become a schema decision, not a deployment puzzle.

GLOBAL Tables — Read-Anywhere

For reference data (currency tables, product catalogs, country lists) that is read in every region but rarely written:

Global locality


CREATE TABLE country_codes (
  code     STRING(2) PRIMARY KEY,
  name     STRING NOT NULL
) LOCALITY GLOBAL;

CockroachDB uses non-blocking transactions to make these tables look like they have a leaseholder in every region. Reads are fast everywhere; writes are slow (they wait long enough that all regions can safely serve the new value).

Rule of thumb: if you write to it more than ~once an hour per row, GLOBAL is the wrong choice.

Node Decommissioning & Recovery

Removing a node cleanly


# Tell node 4 to drain — it stops being a leaseholder and rebalances replicas off
cockroach node decommission 4 --host=<node1>:26257

# Watch progress
cockroach node status --host=<node1>:26257 --decommission
  • Decommissioning is online — no downtime, no read/write interruption
  • The cluster waits until every range has a replacement replica before marking the node decommissioned
  • Use this for: scale-down, hardware retirement, planned maintenance, region evacuation

Recovery From an Unplanned Loss

What CockroachDB does automatically


T+0     Node 3 disappears (kernel panic, network partition, ...)
T+9s    Lease on Node 3's ranges expires; peers acquire new leases
T+5min  Allocator decides: too few replicas, start re-replicating
        Each affected range starts streaming a snapshot to a new node
T+...   When every range is back to 3 replicas, the cluster is healthy again

Operator response: usually none, unless the node was permanently lost. Use the DB Console's Replication dashboard to confirm under-replicated ranges return to zero.

💾 8. Backup, Restore & Change Data Capture

Backup Types

TypeWhat it capturesUse for
Full Complete cluster/db/table at one timestamp Weekly anchor
Incremental Changes since previous full or incremental Daily/hourly
Scheduled Recurring full + incrementals on a cron Production default

Backups are online — they don't lock tables. They snapshot a consistent point-in-time view via MVCC.

Backup & Restore Syntax

Common backup commands


-- Full cluster backup to cloud storage
BACKUP INTO 's3://my-bucket/backups?AWS_ACCESS_KEY_ID=...&AWS_SECRET_ACCESS_KEY=...';

-- Backup a single database
BACKUP DATABASE bank INTO 's3://my-bucket/backups';

-- Incremental — same destination, CockroachDB figures out the diff
BACKUP INTO LATEST IN 's3://my-bucket/backups';

-- Schedule (runs forever)
CREATE SCHEDULE bank_daily
  FOR BACKUP DATABASE bank INTO 's3://my-bucket/backups'
  RECURRING '@daily'
  FULL BACKUP '@weekly';

Restore & Point-in-Time Recovery

Restore scenarios


-- Restore the latest backup of a database into a new name
RESTORE DATABASE bank FROM LATEST IN 's3://my-bucket/backups'
  WITH new_db_name = 'bank_restored';

-- Restore a single table
RESTORE TABLE bank.accounts FROM LATEST IN 's3://my-bucket/backups';

-- Point-in-time restore (must have backup chain covering that time)
RESTORE FROM LATEST IN 's3://my-bucket/backups'
  AS OF SYSTEM TIME '2026-05-22 09:30:00';

Point-in-time recovery requires both a backup chain that includes the target time AND that the cluster's gc.ttlseconds (default 25 hours) hasn't expired the relevant MVCC versions.

Changefeeds — CDC Built In

Stream every row change out to Kafka, a webhook, or cloud pub/sub:

Creating a changefeed


-- To Kafka
CREATE CHANGEFEED FOR TABLE orders, customers
  INTO 'kafka://kafka.example.com:9092'
  WITH updated, resolved = '10s';

-- To an HTTPS webhook
CREATE CHANGEFEED FOR TABLE orders
  INTO 'webhook-https://api.example.com/cdc'
  WITH updated, resolved;

-- To Google Pub/Sub
CREATE CHANGEFEED FOR TABLE orders
  INTO 'gcpubsub://my-project?topic_name=orders';
  • Exactly-once delivery semantics (with proper sink config)
  • JSON or Avro payloads
  • resolved timestamps let downstream systems know "everything before T is final"
  • Driven by jobs system — restartable, monitorable, pausable

🔐 9. Security & Access Control

TLS Everywhere

Production CockroachDB clusters require TLS for both node-to-node and client-to-node communication. --insecure is for labs only.

Generating certs the easy way


mkdir certs my-safe-directory

# CA — kept on a secure machine, not on the cluster nodes
cockroach cert create-ca \
  --certs-dir=certs --ca-key=my-safe-directory/ca.key

# Per-node cert (one per IP/hostname the node serves on)
cockroach cert create-node \
  node1.example.com \
  --certs-dir=certs --ca-key=my-safe-directory/ca.key

# Client cert for the root user
cockroach cert create-client root \
  --certs-dir=certs --ca-key=my-safe-directory/ca.key

For Kubernetes, cockroach-operator and cert-manager handle this. For VMs, distribute ca.crt, node.crt, node.key via your config-management tool.

Authentication Methods

MethodUse for
Certificate Service-to-service; CI; root admin
Password (SCRAM-SHA-256) Humans without a cert; legacy app users
SSO (OIDC, SAML) Centrally-managed human access via your IdP
GSSAPI / Kerberos Existing Kerberos environments

RBAC — Roles, Users, Grants

Setting up a least-privilege app user


-- Roles are reusable bundles of permissions
CREATE ROLE app_readwrite;
GRANT CONNECT ON DATABASE bank TO app_readwrite;
GRANT USAGE  ON SCHEMA   bank.public TO app_readwrite;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA bank.public TO app_readwrite;

-- Future tables auto-pick up the grant
ALTER DEFAULT PRIVILEGES IN SCHEMA bank.public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_readwrite;

-- A user is just a role with LOGIN
CREATE USER bank_app WITH PASSWORD 's3cret-from-vault';
GRANT app_readwrite TO bank_app;

Audit Logging

Capture every DDL change, privilege change, and (optionally) every statement:

Enabling SQL audit


-- Per-table audit
ALTER TABLE bank.accounts EXPERIMENTAL_AUDIT SET READ WRITE;

-- Cluster-wide audit settings
SET CLUSTER SETTING sql.log.user_audit.enabled = true;
SET CLUSTER SETTING sql.log.all_statements.enabled = true;

Output goes to the structured log streams (SENSITIVE_ACCESS, USER_ADMIN, PRIVILEGES). Pipe them into your SIEM with the logging sink config (--log YAML).

📈 10. Monitoring & Troubleshooting

The Four Numbers to Watch

  1. Liveness — number of live nodes
  2. Under-replicated ranges — should be 0 in steady state
  3. SQL p99 latency — for both reads and writes
  4. Storage usage per node — alert at 80%

Everything else is a follow-up question once one of these is wrong.

Prometheus & Grafana

Every CockroachDB node exposes Prometheus metrics on its HTTP port:

Scraping


# prometheus.yml
scrape_configs:
  - job_name: 'cockroachdb'
    metrics_path: /_status/vars
    static_configs:
      - targets: ['n1:8080', 'n2:8080', 'n3:8080']
    scheme: https
    tls_config:
      ca_file: /etc/prom/ca.crt

Cockroach Labs publishes ready-made Grafana dashboards (search "CockroachDB" on grafana.com). They cover overview, SQL, storage, replication, runtime, and changefeeds.

Alerting — Where to Start

AlertSeverityWhat it means
liveness_livenodes < expected Page A node is dead
ranges_underreplicated > 0 for 15 min Page Data at risk; rebalancing failing
capacity_available < 20% Page Disk filling
sql_service_latency p99 > SLO Ticket Tune queries / capacity
sql_distsql_exec_latency.high spike Ticket Cross-region scan or hotspot

Statement Diagnostics

The DB Console can capture a full per-statement bundle including plan, traces, and stats:

Capturing


DB Console → SQL Activity → Statements → click a statement → "Activate diagnostics"
            → Run the query → "Download bundle"

The bundle is a zip you can share with support or analyze locally. It's the single most useful artifact for any "why is this query slow" investigation.

Debug Zip — For Cluster-Wide Issues

Collect everything


cockroach debug zip \
  --host=<node>:26257 \
  --certs-dir=certs \
  cluster-debug.zip
  • Pulls logs, goroutine dumps, range info, schemas, settings from every node
  • Best practice: capture during the incident, not after
  • Share with Cockroach Labs support for escalation

🔗 11. Schema Migrations & Application Integration

Online Schema Changes

CockroachDB performs most DDL online and non-blocking using a background job:

Common online changes


-- Add a NOT NULL column with default — backfilled in the background
ALTER TABLE orders ADD COLUMN total_with_tax DECIMAL(12,2) NOT NULL DEFAULT 0;

-- Add an index — index builds online; queries keep running
CREATE INDEX ON orders(customer_id, status);

-- Drop an index — instant on the query plan, async cleanup
DROP INDEX orders_customer_id_idx;

-- Watch progress
SHOW JOBS WHERE job_type IN ('SCHEMA CHANGE', 'NEW SCHEMA CHANGE');

Differences From PostgreSQL Migrations

🆗 Easier on CockroachDB

  • No ACCESS EXCLUSIVE lock for ADD COLUMN with DEFAULT
  • No table rewrite for adding nullable columns
  • Index builds don't block reads or writes

⚠️ Watch out

  • Some PG migration tools assume BEGIN; ALTER ...; COMMIT — that's fine, but they may also assume CREATE INDEX CONCURRENTLY syntax (use plain CREATE INDEX)
  • Schema changes in an explicit txn are limited
  • Long-running migrations show up as jobs, not session activity — watch them via SHOW JOBS

Connection Pooling — Mandatory at Scale

CockroachDB doesn't pool connections internally — each connection is a goroutine on the server. Use a pooler in front:

Practical guidance


• PgBouncer / Odyssey       — same as PostgreSQL; pool mode "transaction" works
• Cloud-managed pools       — CockroachDB Cloud includes a built-in pooler
• App-side pools (HikariCP, sqlx::Pool, etc.) — fine for moderate scale

Rules of thumb
  - 4-8 active connections per CPU core, cluster-wide
  - Don't run "thousands of clients with one connection each" — pool them
  - Long-running idle connections still cost — set max idle low

Application-Side Retry — Recap

Every CockroachDB-aware app needs a retry path. The pattern is the same in every language:

  1. Open a transaction
  2. Run statements
  3. If COMMIT (or any statement) returns SQLSTATE 40001, restart from step 1
  4. Cap retries (e.g. 5) and surface failure if exhausted
  5. Log the retry count — high counts indicate a contention hotspot to investigate

CI/CD Integration Tips

  • Use migration tools (Flyway, Liquibase, Atlas, golang-migrate, Alembic) — all work with the PG driver
  • Run migrations from one place — don't race multiple CI jobs against the same DDL
  • For ephemeral integration tests, cockroach demo is faster than spinning up a real cluster
  • Test against the same major version as production — feature differences exist between releases
  • Pre-deploy: take a backup, even on small migrations — undo is trivial then
