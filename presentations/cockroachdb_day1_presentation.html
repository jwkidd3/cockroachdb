🪳 1. Introduction to CockroachDB

What Is CockroachDB?

  • Distributed SQL — a single logical SQL database spread across many nodes
  • Strongly consistent by default (serializable isolation)
  • Horizontally scalable — add nodes, get more capacity, no resharding
  • PostgreSQL wire-compatible — drivers, ORMs, and most tools just work
  • Survives disk, machine, rack, datacenter, and region failures

Built by ex-Googlers inspired by Google Spanner — but open source and self-hostable.

Why the Name?

Cockroaches are famous for surviving anything — nuclear winter, earthquakes, dropped boots.

CockroachDB is named for the same property: kill any node, any zone, any region, and the database keeps serving reads and writes.

This isn't a marketing claim — it's an architectural invariant. Every range of data is replicated to 3 (or 5, or 7) nodes by default, and writes only commit when a quorum of replicas has acknowledged them. Survivability is built into the storage layer, not bolted on as a failover script.

The Distributed SQL Landscape

System Model Wire Protocol Notes
PostgreSQL Single primary + read replicas PG Vertical scale; failover is operational
Google Spanner Distributed SQL gRPC / Spanner SQL Managed-only; needs TrueTime atomic clocks
CockroachDB Distributed SQL PG Self-hostable; HLC-based consistency
YugabyteDB Distributed SQL PG & Cassandra Reuses PG query layer; different storage layer
TiDB Distributed SQL MySQL HTAP-focused; TiKV + TiFlash

CockroachDB vs PostgreSQL

👍 What's the Same

  • SQL syntax (SELECT, JOIN, CTEs, window functions)
  • PostgreSQL wire protocol
  • Most drivers and ORMs
  • Transactions, foreign keys, indexes

⚠️ What's Different

  • No stored procedures (functions only)
  • Limited trigger support
  • No extensions (no PostGIS, but spatial is built in)
  • Always SERIALIZABLE — not READ COMMITTED by default
  • Sequences are slower than UUID

When Is CockroachDB the Right Fit?

✅ Great Fit

  • Always-on systems (no maintenance windows)
  • Multi-region or global apps
  • Outgrew a single PostgreSQL primary
  • Regulated data with locality requirements (GDPR, data residency)
  • Financial & transactional systems needing strong consistency

🤔 Probably Not

  • Heavy OLAP / data-warehouse workloads (use a warehouse)
  • Apps deeply dependent on PG extensions
  • Very low concurrency, single-region, small data — PG is simpler
  • Workloads dominated by long-running analytic queries

Real-World Use Cases

  • Financial services — payments, ledgers, fraud (DoorDash, Bose, Lush)
  • Retail & commerce — inventory, order management, carts
  • Gaming — player state, leaderboards, in-game economies
  • SaaS multi-tenant platforms — per-region tenant data residency
  • Identity & authorization — globally-consistent session state

Common thread: strong consistency + survivability + scale. Any two are easy. All three is hard — and that's CockroachDB's niche.

🏗️ 2. Core Architecture

The Big Picture

From the top down, CockroachDB is a stack of layers — each one solves a specific problem:

Layers (top to bottom)


SQL                ← parser, planner, executor, optimizer
  ↓
Transaction        ← serializable isolation, 2-phase commit
  ↓
Distribution       ← splits, merges, routing
  ↓
Replication        ← Raft consensus, leaseholders
  ↓
Storage (Pebble)   ← LSM-tree, MVCC key-value store

Each node runs all layers. There is no separate "router" or "coordinator" tier.

It's All Key-Value Underneath

Every SQL row, every index entry, every system metadata record is stored as a key-value pair in Pebble (CockroachDB's LSM-tree storage engine).

SQL → KV Example


-- Logical SQL:
CREATE TABLE users (id UUID PRIMARY KEY, email STRING, name STRING);
INSERT INTO users VALUES ('abc-123', 'jane@example.com', 'Jane');

-- Physical KV (simplified):
/Table/users/primary/'abc-123'/email  →  'jane@example.com'
/Table/users/primary/'abc-123'/name   →  'Jane'

Why this matters: the layout of your primary key directly determines how rows are distributed across the cluster. Sequential keys = hotspots. Random keys = balanced load. We'll dig into this in Module 1 Section 4.

Ranges — The Unit of Distribution

  • The KV keyspace is sorted and divided into contiguous ranges
  • Default range target size: ~512 MiB
  • When a range grows past the target, it splits automatically
  • When ranges shrink, they can merge
  • Each range is independently replicated and routed

A table doesn't live "on a node" — it lives across however many ranges its data fills, and each range can be on a different set of nodes.

Replication — 3 Copies by Default

Every range is replicated to N nodes (default N=3). The replicas form a Raft group.

Range r42 spread across a 5-node cluster


       ┌───────┐   ┌───────┐   ┌───────┐   ┌───────┐   ┌───────┐
       │ Node1 │   │ Node2 │   │ Node3 │   │ Node4 │   │ Node5 │
       └───────┘   └───────┘   └───────┘   └───────┘   └───────┘
        r42 ▲      r42         r42
        leader     follower    follower

The 3 replicas of r42 elect a leader via Raft. The leader proposes writes; followers ack. A write commits when a majority (2 of 3) acknowledges — so the cluster tolerates losing 1 replica per range with zero data loss and no manual failover.

Raft Consensus in 60 Seconds

📜 What Raft guarantees

  • All replicas agree on the order of writes
  • A committed write is durable as long as a majority of replicas survive
  • If the leader dies, followers elect a new one

🔢 Quorum math

  • 3 replicas → tolerate 1 loss
  • 5 replicas → tolerate 2 losses
  • 7 replicas → tolerate 3 losses

Odd numbers because majority = ⌊N/2⌋ + 1.

Leaseholder — Single Source of Truth for Reads

One of the replicas in each Raft group is also designated the leaseholder. The leaseholder serves all reads for its range without needing to talk to the other replicas.

  • Leader (Raft): proposes writes; usually same node as leaseholder
  • Leaseholder: serves reads; coordinates writes
  • Followers: apply Raft log; can serve follower reads (stale snapshots)

Reads from a leaseholder are strongly consistent — they reflect every committed write. The leaseholder's lease is time-bounded (~9s), so a dead leaseholder is replaced quickly by a peer.

Multi-Active Availability

🐘 Traditional Primary/Replica

  • One writable primary at a time
  • Failover takes seconds to minutes
  • Risk of split-brain & data loss
  • Replicas are read-only

🪳 CockroachDB Multi-Active

  • Every node accepts reads & writes
  • No failover — quorum carries on
  • No split-brain (Raft prevents it)
  • No "follower" lag for writes

Apps point at any node — typically through a load balancer — and the cluster routes the request to the right leaseholder internally.

Node Communication & Gossip

Every node maintains a cluster-wide view of metadata via a gossip protocol:

  • Liveness — which nodes are alive (heartbeats)
  • Range descriptors — where each range's replicas live
  • Capacity & load — used by the rebalancer
  • Node attributes & locality — region, zone, rack

Gossip is eventually consistent — but the actual data and Raft log are strongly consistent. The distinction matters: gossip just tells nodes where to look; consistency comes from Raft.

Cluster Membership & Join Flow

Bringing a new node online


1.  Operator runs:   cockroach start --join=:26257
2.  New node connects to one or more existing nodes (the "join list")
3.  Gossip propagates the new node's address & locality
4.  The allocator decides which ranges should add this node as a replica
5.  Raft snapshots stream existing data to the new node
6.  New node is now a full participant — no manual intervention required

Decommissioning is the reverse: a single command (cockroach node decommission <id>) removes a node, and the allocator drains its replicas to remaining nodes before it shuts down.

Architecture Quick Quiz

Q1. Range r42 has 3 replicas. Two nodes hosting those replicas go down at the same time. What happens?

A: The remaining replica cannot achieve quorum, so r42 becomes unavailable for reads and writes until a peer comes back online. Other ranges with surviving quorum keep serving.

Q2. An application connects to Node 3 and runs SELECT * FROM users WHERE id = 'abc'. The leaseholder for that row is on Node 1. What does Node 3 do?

A: Node 3 routes the request to Node 1's leaseholder via internal RPC and returns the result. The client never sees the redirect.

🛠️ 3. Installation, Configuration & Tooling

One Binary, No Dependencies

CockroachDB ships as a single statically-linked binary called cockroach. It contains:

  • The server (every node, every role)
  • The SQL client (cockroach sql)
  • The demo cluster runner (cockroach demo)
  • Backup/restore, debug, decommission, and admin tooling

No JVM. No Python runtime. No package manager dependencies. scp the binary, run it, done.

Installing

macOS (Homebrew)


brew install \
  cockroachdb/tap/cockroach

cockroach version

Linux / macOS (manual)


curl https://binaries.cockroachdb.com/\
cockroach-latest.linux-amd64.tgz | tar -xz

sudo mv cockroach-*/cockroach \
  /usr/local/bin/

cockroach version

Windows: download the ZIP from the releases page, extract, and add the folder to PATH.

🗂️ 4. SQL Dialect & Schema Design

The Most Important Decision: Primary Keys

The primary key is the physical sort order of a table's KV data. Choose it badly and you create a hotspot; choose it well and the cluster spreads load evenly.

❌ Classic Anti-Pattern


CREATE TABLE events (
  id        SERIAL PRIMARY KEY,
  payload   JSONB,
  created   TIMESTAMP DEFAULT now()
);

Sequential id values → every insert lands on the rightmost range → one leaseholder is hammered while others idle.

SERIAL Is Not What You Think

In PostgreSQL, SERIAL is a sequence-backed counter (1, 2, 3, ...). In CockroachDB, SERIAL is not sequential — by default it's unique_rowid():

unique_rowid() — 64-bit integers, time-prefixed


| 48 bits HLC timestamp | 16 bits node ID + counter |

Better than PG's SERIAL — values are roughly time-ordered but each node carves out its own counter space, so writes spread across the cluster.

Still not random — values are monotonic, so all inserts cluster on the latest range. For high-throughput inserts, prefer UUID.

UUID — The Default Choice

Recommended pattern for high-write tables


CREATE TABLE events (
  id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payload   JSONB,
  created   TIMESTAMPTZ DEFAULT now()
);
  • gen_random_uuid() produces 128 random bits — writes scatter across all ranges
  • No "rightmost range" hotspot
  • Tradeoff: bigger keys (16 bytes vs 8) and no natural ordering

Watch out: if you need ordered iteration by insert time, add a created_at index — don't try to encode ordering into the primary key.

Sequences — Use Sparingly

When you really need gapless integers


CREATE SEQUENCE invoice_seq;

CREATE TABLE invoices (
  id    INT8 PRIMARY KEY DEFAULT nextval('invoice_seq'),
  ...
);

Performance trap: every nextval() is a distributed transaction — it must atomically increment a shared counter range. High-volume inserts on a sequence-PK table will not scale.

Use sequences when business logic requires monotonic integers (e.g. invoice numbers for accounting). Otherwise, use UUID.

Hash-Sharded Indexes — Spread Sequential Keys

Sometimes you genuinely need a monotonic key (e.g. an (account_id, created_at) index for time-range queries). Hash sharding spreads it across N virtual buckets:

Hash-sharded primary key


CREATE TABLE events (
  account_id  UUID,
  created     TIMESTAMPTZ DEFAULT now(),
  payload     JSONB,
  PRIMARY KEY (account_id, created) USING HASH WITH (bucket_count = 16)
);

Under the hood, CockroachDB prepends a hidden crdb_internal_account_id_created_shard_16 column (a hash bucket 0–15) to the key, so writes for similar timestamps land on different ranges.

Range queries by exact (account_id, created) still work via index lookup. Open-ended scans on created alone may need a separate non-sharded secondary index.

Composite Primary Keys

Common multi-tenant pattern


CREATE TABLE orders (
  tenant_id  UUID,
  order_id   UUID DEFAULT gen_random_uuid(),
  customer   STRING,
  total      DECIMAL(12,2),
  PRIMARY KEY (tenant_id, order_id)
);
  • (tenant_id, order_id) co-locates one tenant's data in a contiguous key range
  • Queries filtering by tenant become single-range scans (fast)
  • Sets up cleanly for geo-partitioning later (Day 2 — REGIONAL BY ROW)
  • Hot tenants can still cause a hotspot — be aware

Data Types — PG-Compatible, with Care

👍 Use freely

  • UUID
  • INT8 (always 64-bit)
  • STRING (variable)
  • BYTES
  • TIMESTAMPTZ (TZ-aware)
  • DECIMAL (exact)
  • JSONB
  • BOOL

⚠️ Watch out

  • INT = INT8 (PG defaults to INT4!)
  • FLOAT = FLOAT8
  • SERIAL ≠ PostgreSQL SERIAL
  • TIMESTAMP is TZ-naive — prefer TIMESTAMPTZ
  • NUMERIC = DECIMAL

Constraints & Foreign Keys

Standard SQL, with one wrinkle


CREATE TABLE customers (
  id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email STRING UNIQUE NOT NULL CHECK (length(email) < 256)
);

CREATE TABLE orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id UUID NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  total       DECIMAL(12,2) NOT NULL CHECK (total >= 0)
);

Foreign keys are real and enforced — they require a unique index on the parent column. CockroachDB will warn (or fail) if you try to add an FK without one. Cascading actions work the same way as PG.

Indexes — Same Idea, Slightly Different Costs

  • Secondary indexes are themselves ranges — they replicate just like data
  • Each write to an indexed table writes to every covering index
  • Indexes can be partial (WHERE predicate), covering (STORING clause), or hash-sharded
  • CockroachDB collects table statistics automatically; the cost-based optimizer uses them

Common patterns


-- Plain index
CREATE INDEX ON orders(customer_id);

-- Covering / "storing" index — extra columns travel with the key
CREATE INDEX ON orders(customer_id) STORING (total, status);

-- Partial index — only index "open" orders
CREATE INDEX ON orders(customer_id) WHERE status = 'open';

-- Hash-sharded index — avoid hotspots on time-series patterns
CREATE INDEX ON events(account_id, created)
  USING HASH WITH (bucket_count = 8);

Index Picking — A Mental Model

The optimizer picks an index by estimating how many rows it will read. The fastest plan is the one that scans the fewest keys.

Reading a plan


EXPLAIN SELECT * FROM orders WHERE customer_id = 'abc';

  • scan
    table: orders@orders_customer_id_idx       ← used the secondary index
    spans: [/'abc' - /'abc']                    ← single-key span = great

Anti-pattern signals: full table scan on a large table, span of [ - ] (the whole keyspace), or an estimated row count near the table cardinality.

Storing Clause — "Index-Only" Reads

If a query reads columns not in the indexed key, CockroachDB does an extra primary-key lookup per row. STORING avoids that:

Without vs with STORING


-- Without STORING: index lookup, then PK lookup per row
CREATE INDEX ON orders(customer_id);
SELECT customer_id, total FROM orders WHERE customer_id = 'abc';

-- With STORING: index alone has everything we need
CREATE INDEX ON orders(customer_id) STORING (total, status);
SELECT customer_id, total, status FROM orders WHERE customer_id = 'abc';

Cost: every UPDATE to a stored column must also update the index. Don't blindly add every column to STORING — pick the ones that benefit the hot read path.

Anti-Patterns Cheat-Sheet

PatternWhy It HurtsFix
Sequential PK (SERIAL, sequence) Rightmost-range hotspot UUID or hash-sharded composite
(timestamp) as PK / index lead Same — all writes on latest range Hash-sharded index
Big tables, no FK index FK checks become full scans Index every FK column
SELECT * everywhere Forces PK lookup, defeats covering indexes List columns; add STORING
