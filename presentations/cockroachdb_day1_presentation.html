🪳 1. Introduction to CockroachDB

What Is CockroachDB?

  • Distributed SQL — a single logical SQL database spread across many nodes
  • Strongly consistent by default (serializable isolation)
  • Horizontally scalable — add nodes, get more capacity, no resharding
  • PostgreSQL wire-compatible — drivers, ORMs, and most tools just work
  • Survives disk, machine, rack, datacenter, and region failures

Built by ex-Googlers inspired by Google Spanner — but open source and self-hostable.

Frame it as one sentence: a relational database that speaks PostgreSQL and is built from the ground up to run as a cluster. Everything else in the course follows from the word "cluster".

Head off the first misconception now: it is not PostgreSQL with replication bolted on. There is no primary node. The storage, transaction, and replication layers are original; only the wire protocol and SQL dialect are borrowed.

Terms: SERIALIZABLE — the only isolation level; transactions behave as if run one at a time, and anomalies are prevented by aborting with 40001.

CockroachDB vs PostgreSQL

👍 What's the Same

  • SQL syntax (SELECT, JOIN, CTEs, window functions)
  • PostgreSQL wire protocol
  • Most drivers and ORMs
  • Transactions, foreign keys, indexes

⚠️ What's Different

  • No stored procedures (functions only)
  • Limited trigger support
  • No extensions (no PostGIS, but spatial is built in)
  • Always SERIALIZABLE — not READ COMMITTED by default
  • Sequences are slower than UUID

Walk the table row by row, but spend the time on the two rows that change how students write code: isolation level (SERIALIZABLE always, so retries are normal — Day 2) and primary keys (sequential keys hotspot — later today).

Point out what is the same: the wire protocol, most of the SQL, the drivers. A Postgres developer is productive on day one; the surprises are operational and schema-level, not syntactic.

Terms: SERIALIZABLE — the only isolation level; transactions behave as if run one at a time, and anomalies are prevented by aborting with 40001. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

When Is CockroachDB the Right Fit?

✅ Great Fit

  • Always-on systems (no maintenance windows)
  • Multi-region or global apps
  • Outgrew a single PostgreSQL primary
  • Regulated data with locality requirements (GDPR, data residency)
  • Financial & transactional systems needing strong consistency

🤔 Probably Not

  • Heavy OLAP / data-warehouse workloads (use a warehouse)
  • Apps deeply dependent on PG extensions
  • Very low concurrency, single-region, small data — PG is simpler
  • Workloads dominated by long-running analytic queries

Be honest here; it builds credibility for the rest of the week. It fits when you need survival across failures or regions, horizontal write scaling, or strong consistency across a distributed dataset. It does not fit a single-region, single-node workload that will never grow — Postgres is simpler and faster there.

The tell in a requirements conversation: "what happens when this node / this zone / this region goes away?" If the answer has to be "nothing", you are in CockroachDB territory.

Terms: locality — the --locality startup flag (region=…,zone=…) the allocator uses to spread replicas across failure domains. GLOBAL table — table locality where every region's replica serves current reads; writes commit slightly in the future and are slow everywhere.

🏗️ 2. Core Architecture

The Big Picture

From the top down, CockroachDB is a stack of layers — each one solves a specific problem:

Layers (top to bottom)


SQL                ← parser, planner, executor, optimizer
  ↓
Transaction        ← serializable isolation, 2-phase commit
  ↓
Distribution       ← splits, merges, routing
  ↓
Replication        ← Raft consensus, leaseholders
  ↓
Storage (Pebble)   ← LSM-tree, MVCC key-value store

Each node runs all layers. There is no separate "router" or "coordinator" tier.

This is the layer diagram to return to all week. SQL on top, then the transaction layer, then distribution (ranges), then replication (Raft), then storage (Pebble). A query enters at the top and each layer answers one question: what does this mean, is it consistent, where is it, is it durable, is it on disk.

Tell students you will name the layer every time a concept comes up. It stops the architecture from feeling like a pile of unrelated facts.

Terms: Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. leaseholder — the one replica per range that serves all reads from its local copy and proposes all writes; a new leaseholder must apply every committed write before serving. MVCC — multi-version concurrency control: every write is a new version keyed by timestamp; readers see the version at their timestamp and never block writers. SERIALIZABLE — the only isolation level; transactions behave as if run one at a time, and anomalies are prevented by aborting with 40001. Pebble — CockroachDB's storage engine: an append-only LSM-tree key-value store in Go; no locking. LSM — log-structured merge tree: writes go to a memtable and WAL, flush to immutable sorted files, and are compacted into deeper levels.

It's All Key-Value Underneath

Every SQL row, every index entry, every system metadata record is stored as a key-value pair in Pebble (CockroachDB's LSM-tree storage engine).

SQL → KV Example


-- Logical SQL:
CREATE TABLE users (id UUID PRIMARY KEY, email STRING, name STRING);
INSERT INTO users VALUES ('abc-123', 'jane@example.com', 'Jane');

-- Physical KV (simplified):
/Table/users/primary/'abc-123'/email  →  'jane@example.com'
/Table/users/primary/'abc-123'/name   →  'Jane'

Why this matters: the layout of your primary key directly determines how rows are distributed across the cluster. Sequential keys = hotspots. Random keys = balanced load. We'll dig into this in Module 1 Section 4.

Show the encoding concretely: a row in table 52 with primary key 7 becomes a key like /52/1/7 with the non-key columns as the value. Secondary indexes are just more keys whose value is the primary key. That is the entire storage model.

The payoff comes on the primary-key slides: because rows are sorted by key, the primary key decides which rows sit next to each other on disk and which range they land in. Design the key and you have designed locality.

Terms: hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order. Pebble — CockroachDB's storage engine: an append-only LSM-tree key-value store in Go; no locking. LSM — log-structured merge tree: writes go to a memtable and WAL, flush to immutable sorted files, and are compacted into deeper levels.

Ranges — The Unit of Distribution

  • The KV keyspace is sorted and divided into contiguous ranges
  • Default range target size: ~512 MiB
  • When a range grows past the target, it splits automatically
  • When ranges shrink, they can merge
  • Each range is independently replicated and routed

A table doesn't live "on a node" — it lives across however many ranges its data fills, and each range can be on a different set of nodes.

A range is a contiguous slice of the sorted key space, about 512 MiB in v23.2. It is the thing that gets replicated, moved, split, and merged. Tables and indexes are not distributed; ranges are.

Anticipate the question "how many ranges does my table have?" — SHOW RANGES FROM TABLE, which Lab 1 runs. A new small table is one range; that is why a hot new table can bottleneck on one node until it splits, which is what pre-splitting in Lab 8 addresses.

Units: MiB is a mebibyte, 1,048,576 bytes (220); MB is a megabyte, 1,000,000 bytes — about 5 % apart. CockroachDB uses the binary units throughout: the default range_max_bytes is 536,870,912 bytes, which is exactly 512 MiB (and 537 MB). Zone-config sizes, --cache, --max-sql-memory and the DB Console all report in MiB/GiB. If a student says "megabyte", accept it, but the number on screen is the binary one.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging.

Replication — 3 Copies by Default

Every range is replicated to N nodes (default N=3). The replicas form a Raft group.

Range r42 spread across a 5-node cluster


       ┌───────┐   ┌───────┐   ┌───────┐   ┌───────┐   ┌───────┐
       │ Node1 │   │ Node2 │   │ Node3 │   │ Node4 │   │ Node5 │
       └───────┘   └───────┘   └───────┘   └───────┘   └───────┘
        r42 ▲      r42         r42
        leader     follower    follower

The 3 replicas of r42 elect a leader via Raft. The leader proposes writes; followers ack. A write commits when a majority (2 of 3) acknowledges — so the cluster tolerates losing 1 replica per range with zero data loss and no manual failover.

Three replicas per range, on three different nodes, chosen by the allocator. Replication is synchronous to a majority: a write is acknowledged when 2 of 3 have it durably. There is no asynchronous lag window where a committed write exists on only one node.

Distinguish durability from availability here because students conflate them: a backup gives durability; replicas give both durability and the ability to keep serving when a node dies. Lab 1 Part C demonstrates the second.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. replica — one copy of a range on one store; three per range by default. Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. quorum — a majority of a range's replicas (2 of 3, 3 of 5); needed to commit a write, and to serve at all.

Raft Consensus in 60 Seconds

📜 What Raft guarantees

  • All replicas agree on the order of writes
  • A committed write is durable as long as a majority of replicas survive
  • If the leader dies, followers elect a new one

🔢 Quorum math

  • 3 replicas → tolerate 1 loss
  • 5 replicas → tolerate 2 losses
  • 7 replicas → tolerate 3 losses

Odd numbers because majority = ⌊N/2⌋ + 1.

Keep it to the mechanics students will observe: each range's replicas form a Raft group; one is leader; the leader appends writes to a log and ships them to followers; a majority acknowledging is the commit point; followers apply committed entries in order.

Two properties to state: a committed entry is never lost as long as a majority survives, and a new leader always has every committed entry. Do not go deeper than that — the rest of the protocol never surfaces in operations.

Terms: replica — one copy of a range on one store; three per range by default. Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. quorum — a majority of a range's replicas (2 of 3, 3 of 5); needed to commit a write, and to serve at all.

Leaseholder — Single Source of Truth for Reads

One of the replicas in each Raft group is also designated the leaseholder. The leaseholder serves all reads for its range without needing to talk to the other replicas.

  • Leader (Raft): proposes writes; usually same node as leaseholder
  • Leaseholder: serves reads; coordinates writes
  • Followers: apply Raft log; can serve follower reads (stale snapshots)

Reads from a leaseholder are strongly consistent — they reflect every committed write. The leaseholder's lease is time-bounded (~9s), so a dead leaseholder is replaced quickly by a peer.

This is the slide students misremember, so be precise. Reads do not go through Raft and do not touch a quorum. One replica per range holds the lease; it alone serves reads, from its local copy, and it alone proposes writes. The lease guarantees it has applied every committed write, so a read from it is linearizable.

Consequence: read latency is decided by where the leaseholder is, not where the replicas are. Multi-region design on Day 2 is entirely about leaseholder placement. Lab 1 Part D kills the leaseholder specifically so students see the brief stall while the lease moves.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. replica — one copy of a range on one store; three per range by default. Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. leaseholder — the one replica per range that serves all reads from its local copy and proposes all writes; a new leaseholder must apply every committed write before serving. follower read — a read served by a non-leaseholder replica at a slightly past timestamp it has fully applied (~4–5 s); trades staleness for locality.

Cluster Membership & Join Flow

Bringing a new node online


1.  Operator runs:   cockroach start --join=<existing-node>:26257
2.  New node connects to one or more existing nodes (the "join list")
3.  Gossip propagates the new node's address & locality
4.  The allocator decides which ranges should add this node as a replica
5.  Raft snapshots stream existing data to the new node
6.  New node is now a full participant — no manual intervention required

Lab 1 does both: scripts/crdb add-node, then scripts/crdb run node decommission 3 --insecure. Decommissioning is refused when the replicas have nowhere to go — as on a 3-node cluster at RF=3, which is why the lab adds a fourth node first.

The point to land: there is no master to register with. A new node is given a --join list of any existing nodes, connects, gossips its address, and the allocator starts moving replicas onto it. Adding capacity is starting a process. scripts/crdb add-node in Lab 1 does exactly that.

Decommissioning is the reverse and it is refused when there is nowhere to put the replicas. Lab 1 Part E has students hit that refusal on purpose — a 3-node cluster at replication factor 3 cannot lose a node gracefully — then add a fourth node and succeed.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. replica — one copy of a range on one store; three per range by default. Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. gossip — the peer-to-peer protocol nodes use to share liveness, localities and addresses; eventually consistent, not on the write path. allocator — the loop on every node that adds, removes and moves replicas and leases to satisfy zone configs, liveness, capacity, load and diversity. decommission — online removal of a node: replicas are moved off while it keeps serving; refused when there is nowhere to move them. locality — the --locality startup flag (region=…,zone=…) the allocator uses to spread replicas across failure domains.

🛠️ 3. Installation, Configuration & Tooling

cockroach start — How a Cluster Forms

You type one line…


scripts/crdb up

…and docker/labs.yml runs this, once per node


cockroach start --insecure \
  --advertise-addr=crdb1 \
  --http-addr=0.0.0.0:8080 \
  --join=crdb1:26257,crdb2:26257,crdb3:26257

# Every node gets the SAME --join list. None of them is the "master".
# Then, exactly once in the life of the cluster:
cockroach init --insecure --host=crdb1:26257

Read it in docker/labs.yml; watch a node join with scripts/crdb logs 1. --insecure is for labs only — Lab 12 builds a TLS cluster.

Walk the three flags. --join is the same list on every node; no node is special. --advertise-addr is the name other nodes use to reach this one — inside Docker that is the container name. init runs exactly once in the life of the cluster and turns three waiting processes into a cluster.

Point students at docker/labs.yml so they see this is not hidden magic: the file is the three start commands plus a one-shot init service. scripts/crdb logs 1 shows a node waiting for init and then joining.

From inside another container it is crdb1:26257.

🗂️ 4. SQL Dialect & Schema Design

The Idea This Course Is Built Around

In a single-node database, the primary key answers "which row is this?"
In a distributed database, it also answers "which machine does this row live on, and which machine gets the write?"

The primary key is a distribution decision. Uniqueness is the easy half.

DayWhat that decision turns into
1Range layout and where the hotspot is
2Contention, plan shape, and measured rows/sec (Lab 8)
3Write amplification → node count → hardware bill (Lab 10)
4Outbox design, migration redesign, Kubernetes topology

You will be asked to defend a primary key with a number before this course is over.

State the thesis and repeat it every day: performance in a distributed database is decided by data layout, and data layout is decided by the primary key. Tuning, indexes, and hardware come after that decision, not instead of it.

Everything from here to the end of Day 2 is applications of this one idea. If students remember nothing else, this is the slide.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. contention — transactions touching the same rows at overlapping times; surfaces as waits or retryable errors. hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. write amplification — bytes physically written per byte logically written, from compaction; typically 10–30×, multiplied by replication and indexes. outbox — writing the business row and an event row in one transaction, then publishing the event table with a changefeed; replaces the dual write.

The Most Important Decision: Primary Keys

The primary key is the physical sort order of a table's KV data. Choose it badly and you create a hotspot; choose it well and the cluster spreads load evenly.

❌ Classic Anti-Pattern


CREATE TABLE events (
  id        SERIAL PRIMARY KEY,
  payload   JSONB,
  created   TIMESTAMP DEFAULT now()
);

Sequential id values → every insert lands on the rightmost range → one leaseholder is hammered while others idle.

Three things the primary key controls at once: which rows are adjacent on disk (scan locality), which range a new row lands in (write distribution), and what a point lookup costs (one key or a fan-out). No other schema choice controls all three.

Set the frame for the next four slides: sequential keys concentrate writes, random keys spread them, composite keys choose which queries are local. There is no universally right answer — there is the right answer for a given access pattern.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. leaseholder — the one replica per range that serves all reads from its local copy and proposes all writes; a new leaseholder must apply every committed write before serving. hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. SERIAL — in CockroachDB, unique_rowid() by default: a timestamp-derived, increasing 64-bit value that still hotspots.

SERIAL Is Not What You Think

In PostgreSQL, SERIAL is a sequence-backed counter (1, 2, 3, ...). In CockroachDB, SERIAL is not sequential — by default it's unique_rowid():

unique_rowid() — 64-bit integers, time-prefixed


| 48 bits HLC timestamp | 16 bits node ID + counter |

Better than PG's SERIAL — values are roughly time-ordered but each node carves out its own counter space, so writes spread across the cluster.

Still not random — values are monotonic, so all inserts cluster on the latest range. For high-throughput inserts, prefer UUID.

On a single node, SERIAL is the ideal key. On a cluster it is the worst one: every new row is the largest key so far, so every insert lands on the last range — the right edge — on one leaseholder. Adding nodes does not help; that one range still lives on one node.

Also mention that CockroachDB's SERIAL is not a sequence by default — it is unique_rowid(), a timestamp-derived value, which is still monotonic and still hotspots. Lab 3 measures the difference between SERIAL and UUID under load.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. SERIAL — in CockroachDB, unique_rowid() by default: a timestamp-derived, increasing 64-bit value that still hotspots. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

UUID — The Default Choice

Recommended pattern for high-write tables


CREATE TABLE events (
  id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  payload   JSONB,
  created   TIMESTAMPTZ DEFAULT now()
);
  • gen_random_uuid() produces 128 random bits — writes scatter across all ranges
  • No "rightmost range" hotspot
  • Tradeoff: bigger keys (16 bytes vs 8) and no natural ordering

Watch out: if you need ordered iteration by insert time, add a created_at index — don't try to encode ordering into the primary key.

gen_random_uuid() spreads inserts uniformly across the key space, so a write-heavy table scales with the number of nodes. That is why it is the default recommendation.

State the cost honestly: no time ordering, so "the latest rows" requires a secondary index on a timestamp — which reintroduces a right-edge hotspot on that index. The hash-sharded slide two ahead is how to keep time order without the hotspot.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

Hash-Sharded Indexes — Spread Sequential Keys

When you genuinely need a monotonic key, hash sharding spreads it across N buckets:

Hash-sharded primary key


CREATE TABLE events (
  account_id  UUID,
  created     TIMESTAMPTZ DEFAULT now(),
  id          UUID DEFAULT gen_random_uuid(),   -- per-row tiebreaker
  payload     JSONB,
  PRIMARY KEY (account_id, created, id) USING HASH WITH (bucket_count = 16)
);

Why id is in the key: now() is the transaction timestamp, so every row written by one statement shares it. (account_id, created) alone is not unique and the second row fails with duplicate key value violates unique constraint. A time-series key needs a per-row tiebreaker.

Under the hood a hidden …_shard_16 column (bucket 0–15) is prepended to the key, so near-identical timestamps land on different ranges. Point lookups by (account_id, created) still work; open-ended scans on created alone may want a separate non-sharded index.

Mechanism: a hidden computed column, a hash of the key columns modulo bucket_count, is prepended to the key. Sixteen buckets means sixteen separate key regions; consecutive timestamps land in different ranges. This keeps time order within each bucket while spreading writes.

Two consequences to state. A lookup that supplies all key columns computes the shard and reads one bucket; a lookup on a prefix reads all sixteen buckets in parallel, which is still fast. An open-ended time-range scan with no account_id reads everything — sharding destroys global time order, so a separate plain index may be needed for that query. Also: now() is the transaction timestamp, so (account_id, created) alone is not unique — hence the id tiebreaker. Lab 3 measures all of this.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order. hash-sharded — an index whose key is prefixed with a hidden hash-bucket column, spreading sequential keys across ranges at the cost of global order. bucket_count — the number of virtual shards in a hash-sharded index; each is a separate contiguous key region.

Composite Primary Keys

Common multi-tenant pattern


CREATE TABLE orders (
  tenant_id  UUID,
  order_id   UUID DEFAULT gen_random_uuid(),
  customer   STRING,
  total      DECIMAL(12,2),
  PRIMARY KEY (tenant_id, order_id)
);
  • (tenant_id, order_id) co-locates one tenant's data in a contiguous key range
  • Queries filtering by tenant become single-range scans (fast)
  • Sets up cleanly for geo-partitioning later (Day 2 — REGIONAL BY ROW)
  • Hot tenants can still cause a hotspot — be aware

The order of columns in a composite key is the order rows are sorted, and therefore what is a prefix scan. (tenant_id, created) makes "everything for this tenant, recent first" a single contiguous read; (created, tenant_id) makes it a scan of every tenant.

This is Playbook pattern #3, per-tenant co-location. It also keeps a tenant's transaction inside one range, which is the one-phase commit fast path — cheaper than the cross-range protocol. Lab 3 builds both orderings and compares plans.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. REGIONAL BY ROW — table locality that partitions rows by a region column so each row's leaseholder lives in its home region. hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order. composite key — a primary key of several columns; column order is sort order and decides prefix scans and range co-location.

Constraints & Foreign Keys

Standard SQL, with one wrinkle


CREATE TABLE customers (
  id    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email STRING UNIQUE NOT NULL CHECK (length(email) < 256)
);

CREATE TABLE orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id UUID NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  total       DECIMAL(12,2) NOT NULL CHECK (total >= 0)
);

Enforced, as in PG — the parent column needs a unique index (the PK provides it); cascades work.

The child column gets no index. orders.customer_id is unindexed until you CREATE INDEX ON orders(customer_id); until then every join by customer scans all of orders — the most common slow join in practice.

Foreign keys work and are enforced, but every FK check is a read of the referenced row — which may be on another range and node. On a write-heavy table with an FK to a hot parent, that read is a contention point.

Guidance to give: keep FKs where integrity matters and the parent is stable; consider dropping them on high-volume event tables where the application already guarantees the relationship. Lab 11 hits an FK ordering problem when deleting — parent before child fails.

The warning box is the one to dwell on. PostgreSQL does not index FK columns automatically either, but people forget, and on a distributed database the consequence is a full scan of every range of the child table on every join. Lab 4 Part A shows exactly this: the join runs as a full scan of orders until the index on customer_id exists, then becomes a single-key lookup. The rule: every column that appears in REFERENCES gets an index unless there is a measured reason not to.

Terms: UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

Indexes — Same Idea, Slightly Different Costs

  • Secondary indexes are themselves ranges — they replicate just like data
  • Each write to an indexed table writes to every covering index
  • Indexes can be partial (WHERE predicate), covering (STORING clause), or hash-sharded
  • CockroachDB collects table statistics automatically; the cost-based optimizer uses them

Common patterns


-- Plain index
CREATE INDEX ON orders(customer_id);

-- Covering / "storing" index — extra columns travel with the key
CREATE INDEX ON orders(customer_id) STORING (total, status);

-- Partial index — only index "open" orders
CREATE INDEX ON orders(customer_id) WHERE status = 'open';

-- Hash-sharded index — avoid hotspots on time-series patterns
CREATE INDEX ON events(account_id, created)
  USING HASH WITH (bucket_count = 8);

Secondary indexes are themselves ranges, so they replicate and can hotspot exactly like tables. Every write to an indexed column is another key-value write, another Raft proposal. An index is never free; it is a write cost paid to make one read cheaper.

Walk the four forms on the slide: plain, STORING (covering), partial (WHERE), hash-sharded. Note the syntax order for the last: USING HASH, then STORING, then WITH (bucket_count) — the labs got this wrong once and it is easy to get wrong.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. hotspot — one range's leaseholder doing a disproportionate share of the work, bounding the whole cluster's throughput. hash-sharded — an index whose key is prefixed with a hidden hash-bucket column, spreading sequential keys across ranges at the cost of global order. bucket_count — the number of virtual shards in a hash-sharded index; each is a separate contiguous key region. secondary index — an extra sorted key space whose value is the primary key; itself made of ranges, so it replicates and can hotspot. STORING / covering — STORING copies columns into the index entry's value so the index covers the query with no index join; stored columns cannot be filtered or sorted on. partial index — an index with a WHERE clause containing only matching rows; smaller and cheaper to maintain. statistics — per-table row counts, distinct counts and histograms the optimizer plans from; CREATE STATISTICS name FROM t forces a refresh.

Index Picking — A Mental Model

The optimizer picks an index by estimating how many rows it will read. The fastest plan is the one that scans the fewest keys.

Reading a plan


EXPLAIN SELECT * FROM orders WHERE customer_id = 'abc';

  • scan
    table: orders@orders_customer_id_idx       ← used the secondary index
    spans: [/'abc' - /'abc']                    ← single-key span = great

Anti-pattern signals: full table scan on a large table, span of [ - ] (the whole keyspace), or an estimated row count near the table cardinality.

The optimizer picks the index whose key prefix matches the most selective predicate, then checks whether the index covers the query or needs an index join back to the primary row. Statistics drive the estimate; stale statistics give bad plans.

Teach students to read EXPLAIN for two things: which index was chosen, and whether an index join appears. The second is the signal that a STORING clause would remove a round trip. Lab 4 and Lab 6 practise this.

Terms: secondary index — an extra sorted key space whose value is the primary key; itself made of ranges, so it replicates and can hotspot. EXPLAIN — the plan the optimizer chose from statistics, without executing it.

Storing Clause — "Index-Only" Reads

If a query reads columns not in the indexed key, CockroachDB does an extra primary-key lookup per row. STORING avoids that:

Without vs with STORING


-- Without STORING: index lookup, then PK lookup per row
CREATE INDEX ON orders(customer_id);
SELECT customer_id, total FROM orders WHERE customer_id = 'abc';

-- With STORING: index alone has everything we need
CREATE INDEX ON orders(customer_id) STORING (total, status);
SELECT customer_id, total, status FROM orders WHERE customer_id = 'abc';

Cost: every UPDATE to a stored column must also update the index. Don't blindly add every column to STORING — pick the ones that benefit the hot read path.

STORING copies extra columns into the index entry's value so a query is answered from the index alone — no second lookup into the primary row, no index join. The stored columns are not in the key: they cannot be filtered or sorted on efficiently and do not affect uniqueness; they only ride along.

Rule: columns you filter or sort on go in the key; columns you merely return go in STORING. Cost: every update to a stored column now writes the index too. Lab 4 shows the same query before and after, with the index join disappearing from EXPLAIN ANALYZE.

Terms: STORING / covering — STORING copies columns into the index entry's value so the index covers the query with no index join; stored columns cannot be filtered or sorted on.

Why the Name?

Cockroaches are famous for surviving anything — nuclear winter, earthquakes, dropped boots.

CockroachDB is named for the same property: kill any node, any zone, any region, and the database keeps serving reads and writes.

This isn't a marketing claim — it's an architectural invariant. Every range of data is replicated to 3 (or 5, or 7) nodes by default, and writes only commit when a quorum of replicas has acknowledged them. Survivability is built into the storage layer, not bolted on as a failover script.

The name is a design statement: the goal is survival, not speed. Say this explicitly, because students who arrive from single-node databases expect the pitch to be about performance.

Every later trade-off — synchronous replication, serializable isolation, cross-region write latency — is the price of that goal. When a student asks "why is this slower than Postgres for X", the answer is almost always on this slide.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. replica — one copy of a range on one store; three per range by default. quorum — a majority of a range's replicas (2 of 3, 3 of 5); needed to commit a write, and to serve at all.

The Distributed SQL Landscape

System Model Wire Protocol Notes
PostgreSQL Single primary + read replicas PG Vertical scale; failover is operational
Google Spanner Distributed SQL gRPC / Spanner SQL Managed-only; needs TrueTime atomic clocks
CockroachDB Distributed SQL PG Self-hostable; HLC-based consistency
YugabyteDB Distributed SQL PG & Cassandra Reuses PG query layer; different storage layer
TiDB Distributed SQL MySQL HTAP-focused; TiKV + TiFlash

Two families: databases that shard a single-node engine (Citus, Vitess, application-level sharding) and databases whose storage layer is distributed from the start (CockroachDB, Spanner, YugabyteDB, TiDB). The first family has a coordinator and shards; the second has ranges and consensus.

The practical difference is who handles rebalancing, cross-shard transactions, and failover. In the first family, you do. In the second, the database does. That is the whole reason to accept the second family's costs.

Terms: replica — one copy of a range on one store; three per range by default.

Multi-Active Availability

🐘 Traditional Primary/Replica

  • One writable primary at a time
  • Failover takes seconds to minutes
  • Risk of split-brain & data loss
  • Replicas are read-only

🪳 CockroachDB Multi-Active

  • Every node accepts reads & writes
  • No failover — quorum carries on
  • No split-brain (Raft prevents it)
  • No "follower" lag for writes

Apps point at any node — typically through a load balancer — and the cluster routes the request to the right leaseholder internally.

"Multi-active" means every node accepts reads and writes for the ranges it leads; there is no read-only replica tier and no primary to fail over. Contrast with active-passive (one writer, standby waits) and active-active (multiple writers, conflicts resolved later — which CockroachDB is not).

If asked how this differs from "multi-master": there is exactly one leaseholder per range at any instant, so there is never a write conflict to reconcile. Consensus decides before the write is acknowledged, not after.

Terms: replica — one copy of a range on one store; three per range by default. Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. quorum — a majority of a range's replicas (2 of 3, 3 of 5); needed to commit a write, and to serve at all. leaseholder — the one replica per range that serves all reads from its local copy and proposes all writes; a new leaseholder must apply every committed write before serving. multi-active — every node serves reads and writes for the ranges it leads; no primary, no failover step.

Node Communication & Gossip

Every node maintains a cluster-wide view of metadata via a gossip protocol:

  • Liveness — which nodes are alive (heartbeats)
  • Range descriptors — where each range's replicas live
  • Capacity & load — used by the rebalancer
  • Node attributes & locality — region, zone, rack

Gossip is eventually consistent — but the actual data and Raft log are strongly consistent. The distinction matters: gossip just tells nodes where to look; consistency comes from Raft.

Gossip is how every node learns cluster-wide facts cheaply — who is alive, what localities exist, where ranges' leaseholders roughly are. It is eventually consistent by design and it is not on the write path.

This explains a thing students will see in Lab 1: right after scripts/crdb up, the node list can briefly show fewer than three nodes. The cluster is fine; gossip has not propagated yet. The wrapper waits for it, but the console may lag a moment.

Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. gossip — the peer-to-peer protocol nodes use to share liveness, localities and addresses; eventually consistent, not on the write path. rebalanc — the allocator moving replicas or leases to even out capacity or load, or to repair replication after a failure. locality — the --locality startup flag (region=…,zone=…) the allocator uses to spread replicas across failure domains.

Architecture Quick Quiz

Q1. Range r42 has 3 replicas. Two nodes hosting those replicas go down at the same time. What happens?

A: The remaining replica cannot achieve quorum, so r42 becomes unavailable for reads and writes until a peer comes back online. Other ranges with surviving quorum keep serving.

Q2. An application connects to Node 3 and runs SELECT * FROM users WHERE id = 'abc'. The leaseholder for that row is on Node 1. What does Node 3 do?

A: Node 3 routes the request to Node 1's leaseholder via internal RPC and returns the result. The client never sees the redirect.

Run it as a discussion, not a test. Q1's answer is the one that matters: losing a majority of a range's replicas makes that range unavailable, not inconsistent. The database refuses to answer rather than answer wrongly. That is the design choice everything else rests on.

Q2 establishes that the gateway node is not special — any node accepts the connection and routes internally. Students who came from sharded systems expect to have to connect to the right shard.

  • DECIMAL (exact)
  • JSONB
  • BOOL

⚠️ Watch out

  • INT = INT8 (PG defaults to INT4!)
  • FLOAT = FLOAT8
  • SERIAL ≠ PostgreSQL SERIAL
  • TIMESTAMP is TZ-naive — prefer TIMESTAMPTZ
  • NUMERIC = DECIMAL

Types are PostgreSQL's. The cares: STRING is TEXT; INT is 64-bit; SERIAL is not a sequence; TIMESTAMPTZ over TIMESTAMP; JSONB is fully indexable with inverted indexes; DECIMAL for money, never FLOAT.

The one that surprises migrations: INT defaults to 8 bytes, so a Postgres INT4 column arrives as INT8. Harmless for storage; a mismatch for a driver expecting a 32-bit type.

Terms: SERIAL — in CockroachDB, unique_rowid() by default: a timestamp-derived, increasing 64-bit value that still hotspots. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

Sequences — Use Sparingly

When you really need gapless integers


CREATE SEQUENCE invoice_seq;

CREATE TABLE invoices (
  id    INT8 PRIMARY KEY DEFAULT nextval('invoice_seq'),
  ...
);

Performance trap: every nextval() is a distributed transaction — it must atomically increment a shared counter range. High-volume inserts on a sequence-PK table will not scale.

Use sequences when business logic requires monotonic integers (e.g. invoice numbers for accounting). Otherwise, use UUID.

A sequence is a single row that every insert must increment — a coordination point that hotspots at scale, and a cross-range transaction on every insert. Use it only when an external system demands dense consecutive integers.

If a sequence is unavoidable, CACHE reduces the contention by handing each session a block of values. Point out that this gives up gap-free numbering, which is usually why someone wanted a sequence in the first place.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. UUID — a random 128-bit key (gen_random_uuid()) that spreads inserts uniformly across ranges; no time order.

The one shift to name: "denormalise for read speed" is more often right here than on a single node, because a join can be a cross-node operation. The outbox and per-tenant patterns are both forms of deliberate co-location.

Terms: hash-sharded — an index whose key is prefixed with a hidden hash-bucket column, spreading sequential keys across ranges at the cost of global order. bucket_count — the number of virtual shards in a hash-sharded index; each is a separate contiguous key region. outbox — writing the business row and an event row in one transaction, then publishing the event table with a changefeed; replaces the dual write. TTL — row-level expiry: ttl_expire_after on a table, swept by a background job on a cron. pre-split — seeding a table's ranges before a bulk load so it starts spread across nodes; released with UNSPLIT ALL. IMPORT INTO — bulk load into an existing table from staged files; far faster than INSERT, table briefly offline.
