📊 Section 1: The Observability Stack

What to measure, and what to page on

Two Thousand Metrics, Fifteen That Matter

curl -s http://localhost:8080/_status/vars | wc -l
# ~2000

A dashboard with 200 panels is a dashboard nobody reads. The job is not to display everything — it's to choose the handful that answer "is it healthy?" and "what changed?"

CockroachDB exposes metrics three ways:

  • /_status/vars — Prometheus text format, per node
  • crdb_internal.kv_node_status — the same numbers via SQL
  • DB Console → Metrics — prebuilt dashboards over the same data

The one people miss: txn_restarts_serializable. A rising restart rate is almost always a schema problem surfacing as an ops problem — a single-row counter, a sequential key, an over-wide transaction.

From Metric to SLI to Alert

Recording rules — compute once, use everywhere

- record: crdb:sql_latency:p99
  expr: histogram_quantile(0.99, sum(rate(sql_service_latency_bucket[1m])) by (le))

- record: crdb:sql_success_ratio
  expr: |
    1 - ( sum(rate(sql_failure_count[5m]))
          / clamp_min(sum(rate(sql_query_count[5m])), 1) )

SLO: 99.9% of statements complete under 100 ms over 30 days.
Error budget: 0.1% × 30 days ≈ 43 minutes of "too slow".

Burn-Rate Alerting — Page on Trajectory, Not on Blips

- alert: CRDBLatencySLOFastBurn
  expr: |
    (1 - ( sum(rate(sql_service_latency_bucket{le="0.1"}[1h]))
           / clamp_min(sum(rate(sql_service_latency_count[1h])), 1) ))
    > (14.4 * 0.001)
  for: 5m
  labels: {severity: critical}
Burn rateWindowBudget gone inAction
14.4×1 hour~2 daysPage immediately
6×6 hours~5 daysPage
3×1 day~10 daysTicket
1×3 days30 daysNothing — that's the budget

A threshold alert on "p99 > 100 ms" pages you for a 30-second blip. A burn-rate alert pages you when the month is actually at risk.

📐 Section 2: Capacity Planning & Hardware Sizing

From a throughput target to a purchase order

The Per-Node Budget

ResourceGuidanceWhy
CPU4–16 vCPU; ≥ 8 for productionBelow 4, background work starves foreground SQL
RAM4 GB per vCPUCache 25% + SQL memory 25% + Go heap + page cache
Disk≤ 2.5 TB per nodeRecovery and rebalance time scale with store size
IOPS≥ 500 IOPS, ≥ 30 MB/s per vCPURaft log + LSM compaction are write-amplifying
Network≥ 1 Gb/s; multi-region: latency ≫ bandwidthEvery write is a Raft round trip
Store/CPU~150 GB/vCPU write-heavy
~320 GB/vCPU read-heavy		Compaction cost scales with data per core

Always set --cache=.25 --max-sql-memory=.25. The defaults are laptop-safe, not production-correct. A node should be told it owns the machine.

The Number That Decides Everything: Write Amplification

One logical INSERT into a table with two secondary indexes, at replication factor 3:

1 row  ×  3 KV writes (base + 2 indexes)  ×  3 replicas  =  9 physical writes

Read that again. Adding one index to a hot table increases your write hardware requirement by ~33%. That is a schema decision with a hardware price tag.

This is why Lab 8's "index tax" measurement matters more than any sizing spreadsheet: the spreadsheet takes the index count as an input.

The Sizing Formula

nodes_needed = ceil( target_QPS
                     / (measured_ops_per_node × utilization_target) )

utilization_target = 0.5

Why 0.5 and not 0.8? The cluster must still serve traffic during:

  • A node failure (its load redistributes to the survivors)
  • A rebalance (background replica movement competes for IO)
  • A rolling upgrade (one node down at a time, by design)

Then check the other three constraints — storage capacity, IOPS, and store-per-vCPU — and take the largest node count of the four. The binding constraint is rarely CPU.

Admission Control — Graceful Degradation

When demand exceeds capacity, something has to wait. Admission control chooses what.

SHOW CLUSTER SETTING admission.kv.enabled;              -- true by default
SHOW CLUSTER SETTING admission.sql_kv_response.enabled;

-- Tag a workload so its work is deprioritized
SET default_transaction_quality_of_service = 'background';   -- analytics
SET default_transaction_quality_of_service = 'critical';     -- OLTP

Without admission control, an analytical scan and your checkout path compete as equals and both get slow. With it, the scan queues and checkout keeps its latency. Overload becomes a slowdown of the right thing instead of a collapse of everything.

Benchmarking: Pick the Right Workload

WorkloadShapeAnswers

The trap: kv numbers look glorious and mean almost nothing for an app with joins, indexes, and foreign keys. Use kv for a ceiling; use tpcc for what you'll actually get.

Reading TPC-C Output

_elapsed_______tpmC____efc__avg(ms)__p50(ms)__p99(ms)_pMax(ms)
  180.0s      126.3   98.2%     12.4     11.0     41.9     71.3
  • tpmC — new-order transactions per minute
  • efc — efficiency vs the theoretical 12.86 tpmC per warehouse
  • p99 — the number your users actually feel

Passing = efficiency ≥ 85%. Below that, the cluster is the bottleneck. Raise warehouses until it drops, then find out which resource bound first — CPU, disk, or contention.

TPC-C also teaches schema design by example: every table leads its primary key with the warehouse id. That's the Per-Tenant Co-located PK pattern, and it's why a new-order transaction touches one range instead of nine.

💾 Section 3: Backup, Restore & Disaster Recovery

An untested backup is a hypothesis

The Backup Vocabulary

-- Full, from a slightly stale snapshot so it doesn't fight live traffic
BACKUP DATABASE bank INTO 's3://backups/bank?AUTH=implicit'
  AS OF SYSTEM TIME '-10s'
  WITH revision_history;

-- Incremental — auto-detects its parent
BACKUP DATABASE bank INTO LATEST IN 's3://backups/bank?AUTH=implicit';

-- Inspect without restoring
SHOW BACKUPS IN 's3://backups/bank?AUTH=implicit';
SHOW BACKUP FROM LATEST IN 's3://backups/bank?AUTH=implicit';

AS OF SYSTEM TIME '-10s' on every production backup. revision_history is what makes any timestamp in the window restorable, not just the backup instants.

Restore Shapes

-- Side by side — never straight over the live database during a drill
RESTORE DATABASE bank FROM LATEST IN '...' WITH new_db_name = 'bank_restored';

-- One table into an existing database
RESTORE TABLE bank.public.accounts FROM LATEST IN '...' WITH into_db = 'staging';

-- Point in time
RESTORE DATABASE bank FROM LATEST IN '...' AS OF SYSTEM TIME '2024-06-01 14:02:00';

-- Whole cluster: users, roles, settings too. Needs a fresh cluster.
RESTORE FROM LATEST IN '...';

A database backup does not carry users, roles, or grants. A cluster backup does. Guess which one people discover mid-incident.

RTO and RPO — Honest Arithmetic

worst-case RPO = incremental interval + backup duration + detection time
actual RTO     = locate + restore + verify + cut over
CadenceNominal RPORealistic RPOCost
Hourly incremental1 h~1 h 5 mLow
15-minute incremental15 m~18 mMedium
5-minute incremental5 m~7.7 mHigh
Changefeed to object storesecondssecondsHighest

Your RTO is a measurement, not a policy. Restore a real dataset, time it, divide by size, extrapolate. The number in the runbook is almost always smaller than the number on the stopwatch.

The DR Drill That Counts

✅ A real drill

  • Restores into a different cluster
  • Verifies row counts and a business checksum
  • Confirms users and grants came back
  • Records a measured RTO
  • Ends with an app smoke test

❌ Theatre

  • "The backup job succeeded"
  • Restoring over the source
  • Checking that a row exists
  • An RTO copied from a vendor slide
  • Never testing the runbook on someone else

Swap runbooks with another pair in the lab. If they can't follow yours without asking you a question, it won't work at 3am either.

🔐 Section 4: Security Hardening

Certificates, roles, authentication, audit

TLS Everywhere — and the Rotation Nobody Plans

cockroach cert create-ca     --certs-dir=certs --ca-key=keys/ca.key
cockroach cert create-node   localhost 127.0.0.1 --certs-dir=certs --ca-key=keys/ca.key
cockroach cert create-client root --certs-dir=certs --ca-key=keys/ca.key

Rotation without downtime: reissue the cert, then kill -SIGHUP <pid>. The node reloads certificates in place — open connections stay open.

CertLifetimeRotate at
CA5–10 years50% of life, planned
Node1 year3 months before expiry
Client1 year (shorter for humans)Quarterly, automated

Rotating the CA — Order Matters

1. Append the NEW CA to ca.crt on every node and client   (both trusted)
2. SIGHUP every node
3. Re-issue node and client certs from the new CA, one node at a time
4. Remove the OLD CA from ca.crt
5. SIGHUP every node again

Doing steps 3 and 4 in the wrong order locks you out of your own cluster. Write the procedure down before you need it, and rehearse it on a throwaway cluster.

RBAC That Survives CI/CD

CREATE ROLE ledger_connect;
GRANT CONNECT ON DATABASE ledger TO ledger_connect;
GRANT USAGE ON SCHEMA ledger.public TO ledger_connect;

CREATE ROLE ledger_ro;   GRANT ledger_connect TO ledger_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA ledger.public TO ledger_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA ledger.public GRANT SELECT ON TABLES TO ledger_ro;

CREATE ROLE ledger_rw;   GRANT ledger_ro TO ledger_rw;
CREATE ROLE ledger_migrator; GRANT ledger_rw TO ledger_migrator;
GRANT CREATE ON SCHEMA ledger.public TO ledger_migrator;

Do this first, or the rest is decorative: a new database's public schema grants CREATE to the public role — every user can create objects in it.

REVOKE CREATE ON SCHEMA ledger.public FROM public;

ALTER DEFAULT PRIVILEGES is the feature that matters. Without it, every migration that creates a table also needs a matching GRANT — and the one someone forgets is the one that pages you.

Authentication: HBA and SSO

SET CLUSTER SETTING server.host_based_authentication.configuration = '
# TYPE  DATABASE  USER          ADDRESS  METHOD
host    all       app_user      all      cert
host    all       report_user   all      cert-password
host    all       all           all      scram-sha-256
';
-- DB Console SSO
SET CLUSTER SETTING server.oidc_authentication.enabled = true;
SET CLUSTER SETTING server.oidc_authentication.provider_url = 'https://idp.example.com';
-- SQL client SSO
SET CLUSTER SETTING server.jwt_authentication.enabled = true;

The operational argument for SSO: deprovisioning a human in the IdP removes their database access. Without it, offboarding depends on someone remembering to run DROP USER.

The Audit Pipeline

ALTER TABLE ledger.public.accounts EXPERIMENTAL_AUDIT SET READ WRITE;

Every access produces a structured record on the SENSITIVE_ACCESS channel:

FieldThe auditor's question
TimestampWhen
UserWho
TableNameWhat data
StatementWhat operation
ApplicationNameWhich service
RemoteAddressFrom where

Ship it off-box. An attacker with node access can delete local log files. Audit records that already left the machine cannot be un-sent.

On-Call: What to Capture Before You Escalate

debug zip

cockroach debug zip out.zip \
  --host=... --redact
  • Per-node status and logs
  • Changed cluster settings
  • Range and lease state
  • In-flight queries
  • Contention events
  • Heap and goroutine dumps

Statement bundle

EXPLAIN ANALYZE (DEBUG)
  SELECT ...;
  • Narrower and usually more useful
  • Plan, statistics, trace, environment
  • Reproducible by support
  • Also available in DB Console → Statements

Always --redact anything leaving your organization — a raw zip contains query text with literal values.
