📊 Section 1: The Observability Stack

What to measure, and what to page on

About 10 minutes, five slides. The argument: CockroachDB exports over two thousand metrics; fifteen of them tell you whether the cluster is healthy, and an alert should fire on an SLO burn rate, not on a raw threshold. Log channels are the second half — separating SQL audit and security events from the operational firehose.

Lab 9 builds the whole pipeline: scrape, rules, Grafana dashboard, log channel config.

Two Thousand Metrics, Fifteen That Matter

curl -s http://localhost:8080/_status/vars | wc -l
# ~2000

A dashboard with 200 panels is a dashboard nobody reads. The job is not to display everything — it's to choose the handful that answer "is it healthy?" and "what changed?"

CockroachDB exposes metrics three ways:

  • /_status/vars — Prometheus text format, per node
  • crdb_internal.kv_node_status — the same numbers via SQL
  • DB Console → Metrics — prebuilt dashboards over the same data

The endpoint is /_status/vars on every node, Prometheus format, over two thousand series. Nobody watches two thousand things; the next slide is the short list. Lab 9 scrapes it and confirms each metric on the short list is present.

Make the distinction between node metrics and store metrics now: a node has one or more stores (disks), and capacity, storage-engine, and queue metrics belong to the store. In SQL that is kv_store_status; asking kv_node_status for them returns NULL silently.

Terms: crdb_internal — the virtual schema exposing cluster state in SQL; what the DB Console reads.

From Metric to SLI to Alert

Recording rules — compute once, use everywhere

- record: crdb:sql_latency:p99
  expr: histogram_quantile(0.99, sum(rate(sql_service_latency_bucket[1m])) by (le))

- record: crdb:sql_success_ratio
  expr: |
    1 - ( sum(rate(sql_failure_count[5m]))
          / clamp_min(sum(rate(sql_query_count[5m])), 1) )

SLO: 99.9% of statements complete under 100 ms over 30 days.
Error budget: 0.1% × 30 days ≈ 43 minutes of "too slow".

Metric is the raw series. SLI is the ratio you promise on — requests under 100 ms over total. SLO is the target. Alert fires on the SLO, not the metric. This sequence is why "p99 latency above 200 ms" is a bad alert and "error budget burning 14 times faster than allowed" is a good one.

Lab 9 writes the recording rules that turn the latency histogram into an SLI. Emphasise that the histogram buckets in sql_service_latency_bucket are what makes percentiles possible at all.

Terms: SLI / SLO — SLI: the measured ratio (good requests / total). SLO: the target for it. Alerts fire on the SLO, not the raw metric.

Terms on this slide: p99 — 99th-percentile latency — 1 in 100 requests was slower; the tail users notice · histogram_quantile — PromQL function that estimates a percentile from a histogram’s buckets · clamp_min — PromQL function that raises a value to a floor — used to avoid dividing by zero · sql_service_latency_bucket — the SQL latency histogram exported to Prometheus; bucket bounds in nanoseconds · sql_success_ratio — the lab’s recording rule: 1 − failed statements ÷ all statements · sql_latency — the lab’s recording rules crdb:sql_latency:p50 / p99, in seconds

Burn-Rate Alerting — Page on Trajectory, Not on Blips

- alert: CRDBLatencySLOFastBurn
  expr: |
    (1 - ( sum(rate(sql_service_latency_bucket{le="0.1"}[1h]))
           / clamp_min(sum(rate(sql_service_latency_count[1h])), 1) ))
    > (14.4 * 0.001)
  for: 5m
  labels: {severity: critical}
Burn rateWindowBudget gone inAction
14.4×1 hour~2 daysPage immediately
6×6 hours~5 daysPage
3×1 day~10 daysTicket
1×3 days30 daysNothing — that's the budget

A threshold alert on "p99 > 100 ms" pages you for a 30-second blip. A burn-rate alert pages you when the month is actually at risk.

A burn rate is how fast the error budget is being consumed relative to the rate that would exhaust it exactly at the end of the window. 14x over an hour means the month's budget is gone in two days — page. 1x means on track — do nothing.

The two-window trick (short and long) suppresses blips: both must be over threshold. Lab 9's rules file uses the 1h/5m pair. This is the difference between an on-call rotation people quit and one they tolerate.

Terms: burn rate — how fast the error budget is being consumed relative to the rate that would exhaust it exactly at the window's end.

Every log event belongs to a channel: HEALTH, OPS, SENSITIVE_ACCESS, USER_ADMIN, PRIVILEGES, SQL_EXEC, and so on. A log config routes channels to sinks — files, HTTP, stderr — with per-sink filtering. Production sends security channels to the SIEM and health to ops, separately.

In the labs the config is a file mounted into node 1 by a compose overlay, and node 1 is restarted with it. Lab 9 splits health from security; Lab 12 adds auditable: true to the security sink and ships it off-box.

Terms: rebalanc — the allocator moving replicas or leases to even out capacity or load, or to repair replication after a failure. decommission — online removal of a node: replicas are moved off while it keeps serving; refused when there is nowhere to move them. sink — a changefeed's destination (kafka://, cloud storage, webhook); dialled by the database node, so it must be reachable from inside the cluster network. SENSITIVE_ACCESS — the log channel per-table auditing writes to; route it to an auditable sink. log channel — a named category of log events (HEALTH, OPS, SENSITIVE_ACCESS, …) routed to sinks by a log config file.

Acronyms: OPS — operations (log channel / operators) · SIEM — security information and event management system

📐 Section 2: Capacity Planning & Hardware Sizing

From a throughput target to a purchase order

About 12 minutes, five slides. The per-node budget slide and the write-amplification slide are the core: capacity is (rows × indexes × replicas × version overhead) for storage and a measured per-node throughput ceiling for CPU, sized at 50% utilisation. TPC-C is the benchmark because it exercises transactions and contention, not because anyone runs a warehouse.

Lab 10's Part E — the paper sizing exercises — is the most valuable twenty minutes of the day. Protect it.

Always set --cache=.25 --max-sql-memory=.25. The defaults are laptop-safe, not production-correct. A node should be told it owns the machine.

Rule-of-thumb capacities per vCPU and per node for a tuned workload; the numbers are conservative starting points, not promises. Storage is the one most often undersized, because of the next slide.

The right way to use the budget: estimate, then benchmark (Lab 10), then size from the measurement. The formula slide two ahead does the arithmetic.

Units: the budget figures here are decimal (GB = 109 bytes, the way disks and cloud instance types are sold), while CockroachDB itself reports in binary units (GiB = 230, about 7 % larger per unit). A "150 GB" disk is about 140 GiB in the DB Console. The difference does not change the arithmetic on this slide, but it explains why the console and the invoice never quite agree. Range size is 512 MiB, not 512 MB.

Terms: Raft — the consensus protocol a range's replicas run among themselves; a leader replicates a log to followers and a quorum acknowledging is the commit point. rebalanc — the allocator moving replicas or leases to even out capacity or load, or to repair replication after a failure. LSM — log-structured merge tree: writes go to a memtable and WAL, flush to immutable sorted files, and are compacted into deeper levels. compaction — the LSM background merge of sorted files that discards overwritten versions; the source of write amplification. block cache — Pebble's in-memory cache of data blocks; --cache per node. store — one disk on a node; capacity, storage-engine and queue metrics belong to stores (kv_store_status, not kv_node_status).

Acronyms: CPU — central processing unit · SQL — Structured Query Language · RAM — random-access memory · GB — gigabyte (10⁹ bytes; GiB = 2³⁰) · TB — terabyte · IOPS — I/O operations per second · MB — megabyte (10⁶ bytes; MiB = 2²⁰) · LSM — log-structured merge tree — the storage engine design

Terms on this slide: vCPU — virtual CPU — one hardware thread as presented by the cloud/VM

"Told it owns the machine" means the start flags. CockroachDB never assumes it has the whole host; the defaults are laptop-safe (--cache 128 MiB, --max-sql-memory 25 %). On a dedicated node you start it with cockroach start --cache=.25 --max-sql-memory=.25 …: a quarter of memory for the storage cache, a quarter for SQL working memory, the rest left for the Go heap, Raft and the OS page cache. The percentages are of the memory the process detects — the host’s RAM, or the cgroup limit when a container or pod has one. --store=…,size=… does the same for disk. The lab cluster runs .10/.10 because three nodes share one 8 GB Docker host; at .25 each would size itself as if it owned all 8 GB and the TPC-C import OOM-killed a node.

The Number That Decides Everything: Write Amplification

One logical INSERT into a table with two secondary indexes, at replication factor 3:

1 row  ×  3 KV writes (base + 2 indexes)  ×  3 replicas  =  9 physical writes

Read that again. Adding one index to a hot table increases your write hardware requirement by ~33%. That is a schema decision with a hardware price tag.

This is why Lab 8's "index tax" measurement matters more than any sizing spreadsheet: the spreadsheet takes the index count as an input.

An LSM (Pebble) rewrites data as it compacts down through levels, so one logical write becomes several physical writes — typically 10–30x on a write-heavy table. Disk IOPS budget has to be divided by that number.

Add replication (3x) and secondary indexes (one more logical write each) and a "1 KB insert" can be 100 KB of disk activity. This is why a spinning disk is never adequate and why "we have plenty of IOPS" is usually wrong by an order of magnitude.

Terms: replica — one copy of a range on one store; three per range by default. replication factor — the number of replicas per range (zone config num_replicas); 3 by default, 5 for system ranges and REGION survival. secondary index — an extra sorted key space whose value is the primary key; itself made of ranges, so it replicates and can hotspot. write amplification — bytes physically written per byte logically written, from compaction; typically 10–30×, multiplied by replication and indexes.

Acronyms: KV — key-value — the storage layer under SQL, and the name of the kv workload

The Sizing Formula

nodes_needed = ceil( target_QPS
                     / (measured_ops_per_node × utilization_target) )

utilization_target = 0.5

Why 0.5 and not 0.8? The cluster must still serve traffic during:

  • A node failure (its load redistributes to the survivors)
  • A rebalance (background replica movement competes for IO)
  • A rolling upgrade (one node down at a time, by design)

Then check the other three constraints — storage capacity, IOPS, and store-per-vCPU — and take the largest node count of the four. The binding constraint is rarely CPU.

Walk the arithmetic once with real numbers from the room. Storage: raw data times replication factor times a compaction headroom of about 1.5. IOPS: write rate times amplification times replication. CPU from the per-vCPU budget. Take the largest and add headroom for the allocator's own work and for losing a node.

The step students skip: sizing for N minus one. A 3-node cluster must run on 2 during maintenance.

Terms: replica — one copy of a range on one store; three per range by default. rebalanc — the allocator moving replicas or leases to even out capacity or load, or to repair replication after a failure. store — one disk on a node; capacity, storage-engine and queue metrics belong to stores (kv_store_status, not kv_node_status).

Acronyms: IO — input/output · CPU — central processing unit

Terms on this slide: vCPU — virtual CPU — one hardware thread as presented by the cloud/VM · utilization_target — the fraction of measured capacity you plan to use — 0.5 leaves headroom for failure and upgrades

Passing = efficiency ≥ 85%. Below that, the cluster is the bottleneck. Raise warehouses until it drops, then find out which resource bound first — CPU, disk, or contention.

TPC-C also teaches schema design by example: every table leads its primary key with the warehouse id. That's the Per-Tenant Co-located PK pattern, and it's why a new-order transaction touches one range instead of nine.

💾 Section 3: Backup, Restore & Disaster Recovery

An untested backup is a hypothesis

About 10 minutes, four slides. Vocabulary first (full, incremental, revision history, AS OF SYSTEM TIME, schedules), then the shapes of restore, then RTO/RPO as arithmetic you can measure. The point of “The DR Drill That Counts” is that a backup nobody has restored is a hypothesis.

Licensing comes up: incremental and revision-history backups need a licence; the class licence is applied by scripts/crdb up, so students see nothing. If anyone gets a licence error, their cluster predates .license.env — scripts/crdb reset.

The Backup Vocabulary

-- Full, from a slightly stale snapshot so it doesn't fight live traffic
BACKUP DATABASE bank INTO 's3://backups/bank?AUTH=implicit'
  AS OF SYSTEM TIME '-10s'
  WITH revision_history;

-- Incremental — auto-detects its parent
BACKUP DATABASE bank INTO LATEST IN 's3://backups/bank?AUTH=implicit';

-- Inspect without restoring
SHOW BACKUPS IN 's3://backups/bank?AUTH=implicit';
SHOW BACKUP FROM LATEST IN 's3://backups/bank?AUTH=implicit';

AS OF SYSTEM TIME '-10s' on every production backup. revision_history is what makes any timestamp in the window restorable, not just the backup instants.

Full backup, incremental (changes since the last one), revision_history (every MVCC version, which enables point-in-time restore), and scheduled backups. Cluster backups include users and settings; database backups do not.

State the licence split once: full and cluster backups are free; revision_history and incrementals are enterprise. The class licence is applied by scripts/crdb up, so all of it runs in Lab 11.

Terms: AS OF SYSTEM TIME — a read at a past timestamp, served from retained MVCC history by any replica, without blocking writers. backup: full / incremental / revision_history — full captures every row at one time; incremental captures changes since the last; revision_history keeps every version for point-in-time restore (licensed).

Restore Shapes

-- Side by side — never straight over the live database during a drill
RESTORE DATABASE bank FROM LATEST IN '...' WITH new_db_name = 'bank_restored';

-- One table into an existing database
RESTORE TABLE bank.public.accounts FROM LATEST IN '...' WITH into_db = 'staging';

-- Point in time
RESTORE DATABASE bank FROM LATEST IN '...' AS OF SYSTEM TIME '2024-06-01 14:02:00';

-- Whole cluster: users, roles, settings too. Needs a fresh cluster.
RESTORE FROM LATEST IN '...';

A database backup does not carry users, roles, or grants. A cluster backup does. Guess which one people discover mid-incident.

Restore a table, a database, or the whole cluster; restore into a new name; restore as of a past time (needs revision_history). A full-cluster restore requires an empty target cluster — exactly the DR situation, and why Lab 11's standby is a fresh stack.

The gotcha worth stating: AS OF SYSTEM TIME on a backup taken moments after creating something can predate it. Lab 11 hit this — a user created right before a backup with AOST minus ten seconds was not in the backup.

Rotating Without Downtime

Reissue, then signal the process — no restart, connections stay open

docker compose -f docker/labs-secure.yml kill -s HUP crdbs1

Only if the binary is PID 1. Through a shell-script entrypoint the signal never reaches it: the cert is reissued, cert list shows the new expiry, and the server keeps serving the old one. True of any wrapped process.

RBAC That Survives CI/CD

CREATE ROLE ledger_connect;
GRANT CONNECT ON DATABASE ledger TO ledger_connect;
GRANT USAGE ON SCHEMA ledger.public TO ledger_connect;

CREATE ROLE ledger_ro;   GRANT ledger_connect TO ledger_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA ledger.public TO ledger_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA ledger.public GRANT SELECT ON TABLES TO ledger_ro;

CREATE ROLE ledger_rw;   GRANT ledger_ro TO ledger_rw;
CREATE ROLE ledger_migrator; GRANT ledger_rw TO ledger_migrator;
GRANT CREATE ON SCHEMA ledger.public TO ledger_migrator;

Do this first, or the rest is decorative: a new database's public schema grants CREATE to the public role — every user can create objects in it.

REVOKE CREATE ON SCHEMA ledger.public FROM public;

ALTER DEFAULT PRIVILEGES is the feature that matters. Without it, every migration that creates a table also needs a matching GRANT — and the one someone forgets is the one that pages you.

Role hierarchy: connect, read, write, migrate, each inheriting the last; users are members of exactly one. Two things break this in practice, and Lab 12 hits both. First, a new database's public schema grants CREATE to everyone — revoke it before anything else. Second, default privileges are scoped to the role that creates the table, so root's defaults do not cover tables the migration role creates.

The fix for the second is the CI/CD lesson: the migration role sets its own ALTER DEFAULT PRIVILEGES. Verify with negative tests — report_user must fail to UPDATE — not just positive ones.

Acronyms: RBAC — role-based access control · CI — continuous integration

Admission Control — Graceful Degradation

When demand exceeds capacity, something has to wait. Admission control chooses what.

SHOW CLUSTER SETTING admission.kv.enabled;              -- true by default
SHOW CLUSTER SETTING admission.sql_kv_response.enabled;

-- Tag a workload so its work is deprioritized
SET default_transaction_quality_of_service = 'background';   -- analytics
SET default_transaction_quality_of_service = 'critical';     -- OLTP

Without admission control, an analytical scan and your checkout path compete as equals and both get slow. With it, the scan queues and checkout keeps its latency. Overload becomes a slowdown of the right thing instead of a collapse of everything.

When a node's CPU or storage engine is overloaded, admission control queues lower-priority work rather than letting everything slow down together. Foreground SQL beats background jobs; user-settable priority can push one workload ahead of another.

The metric is admission_wait_durations with a queue suffix. Lab 10 sets default_transaction_quality_of_service to show the knob exists. The teaching point: the cluster degrading gracefully is a feature; seeing admission wait time is the signal to add capacity, not to turn it off.

Terms: admission control — per-node queueing that delays lower-priority work when CPU or storage is saturated, instead of slowing everything. cluster setting — a cluster-wide configuration value set with SET CLUSTER SETTING; distinct from a session variable.

Acronyms: OLTP — online transaction processing

Terms on this slide: default_transaction_quality_of_service — session setting that tags transactions background / regular / critical for admission control

Rotating the CA — Order Matters

1. Append the NEW CA to ca.crt on every node and client   (both trusted)
2. SIGHUP every node
3. Re-issue node and client certs from the new CA, one node at a time
4. Remove the OLD CA from ca.crt
5. SIGHUP every node again

Doing steps 3 and 4 in the wrong order locks you out of your own cluster. Write the procedure down before you need it, and rehearse it on a throwaway cluster.

Both CAs must be trusted everywhere before any cert is reissued from the new one, and the old CA is removed only after every cert has moved. Do steps 3 and 4 in the wrong order and the cluster cannot talk to itself.

Have students write the order down. Nobody rotates a CA often enough to remember it under pressure.

Terms: SIGHUP — the signal that makes a node reload its certificates in place, without a restart.

Acronyms: CA — certificate authority · SIGHUP — the hang-up signal, used to make a process reload configuration

debug zip

cockroach debug zip out.zip \
  --host=... --redact
  • Per-node status and logs
  • Changed cluster settings
  • Range and lease state
  • In-flight queries
  • Contention events
  • Heap and goroutine dumps

Statement bundle

EXPLAIN ANALYZE (DEBUG)
  SELECT ...;
  • Narrower and usually more useful
  • Plan, statistics, trace, environment
  • Reproducible by support
  • Also available in DB Console → Statements

Always --redact anything leaving your organization — a raw zip contains query text with literal values.

cockroach debug zip collects logs, settings, node status, ranges, jobs, and statement statistics into one archive — the thing support asks for first. --redact strips query literals for cases where the data is sensitive. EXPLAIN ANALYZE (DEBUG) does the same for one statement.

In this course the zip is written inside the node and copied out with scripts/crdb cp. Lab 9 produces both the full and redacted versions and inspects the contents.

Terms: range — a contiguous slice of the sorted key space (~512 MiB) and the unit of replication, rebalancing, splitting and merging. leaseholder — the one replica per range that serves all reads from its local copy and proposes all writes; a new leaseholder must apply every committed write before serving. contention — transactions touching the same rows at overlapping times; surfaces as waits or retryable errors. EXPLAIN ANALYZE — runs the query and reports actual rows read vs returned, per-operator time, and which nodes did the work. statistics — per-table row counts, distinct counts and histograms the optimizer plans from; CREATE STATISTICS name FROM t forces a refresh. cluster setting — a cluster-wide configuration value set with SET CLUSTER SETTING; distinct from a session variable.
